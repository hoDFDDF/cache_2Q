# LFU: e2e-тесты и бенчмарк хитов

## Простой Python-вариант с графиками и Excel

Первоначальная настройка из корня проекта:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r Tests/e2e_tests/requirements.txt
cmake -S . -B build
cmake --build build --target LFU-cache -j 4
```

Обычный запуск:

```sh
python Tests/e2e_tests/lfu_benchmark.py
```

По умолчанию: 100 000 запросов, 10 000 возможных целочисленных ключей,
ёмкости 100/500/1000, alpha 0.8/1.0/1.2, seed 42. Параметры можно изменить:

```sh
python Tests/e2e_tests/lfu_benchmark.py \
    --requests 100000 --keys 10000 \
    --capacities 100 500 1000 2000 \
    --alphas 0.8 1.0 1.2 --seed 42
```

В Python-версии списки задаются **через пробелы**. `--cache-bin PATH` позволяет
указать другой исполняемый файл, `--output DIR` — другую папку результатов.
Все параметры доступны через `--help`.

Каждый запуск создаёт отдельную папку в `build/lfu_python_results/`:

- **`results.xlsx`** — готовая таблица для Excel с числовыми ячейками,
  процентным форматом hit_rate, фильтром и закреплённой строкой заголовков.
- **`plots.png`** — hit rate в зависимости от ёмкости и сравнение частот
  с теоретическим распределением Ципфа для первых 100 ключей.
- `results.csv` — дополнительная таблица, разделитель `;`, кодировка UTF-8 BOM.
- `inputs/` — вход, stdout и stderr каждого запуска C++-кеша.

Открывайте `results.xlsx` двойным щелчком: выбирать разделитель не требуется.

Генерация реализована явно: `weights = keys.astype(float) ** (-alpha)`,
затем `probabilities = weights / weights.sum()` и
[`rng.choice(keys, size=requests_count, p=probabilities)`](https://numpy.org/doc/stable/reference/random/generated/numpy.random.Generator.choice.html).
Для одного alpha все ёмкости получают одинаковый поток. Каждый запуск кеша
начинается с пустого состояния. Python сверяет хиты с отдельной LFU/LRU-моделью
на словаре и куче; `FAIL` приводит к коду возврата 1.

Один seed воспроизводит результат в том же окружении NumPy. Генераторы Python
и C++ различаются: их потоки и числа хитов при одинаковом seed могут отличаться.
Копирование кеша этот бенчмарк не проверяет. Здесь измеряется число хитов,
а не скорость выполнения. Для сохранения PNG используется неграфический backend;
окно с графиком автоматически не открывается.

## C++-вариант

`lfu_benchmark.cpp` — C++-программа для macOS/Linux. Она генерирует запросы,
запускает **отдельный процесс `LFU-cache`** и сравнивает число хитов с независимой
эталонной LFU-моделью. Python для этих тестов не требуется.

## Сборка и быстрые проверки

Из корня репозитория:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --target lfu_benchmark -j 4
ctest --test-dir build -R '^lfu_e2e_' --output-on-failure
```

Таргет `lfu_benchmark` автоматически собирает `LFU-cache`.

- `lfu_e2e_edges`: 8 случаев с заранее известным ответом — пустой поток,
  нулевая ёмкость, повтор одного ключа, уникальные ключи, весь набор помещается
  в кеш, LFU-вытеснение, LRU при равных частотах, границы `int`.
- `lfu_e2e_zipf`: 30 запусков — 3 показателя Ципфа × 2 seed × 5 ёмкостей,
  по 3000 запросов. Включает ёмкости 0, 1 и больше числа возможных ключей.

## Запуск бенчмарка

```sh
./build/Tests/lfu_benchmark \
    --cache-bin ./build/modules/LFU-cache \
    --requests 100000 \
    --keys 10000 \
    --capacities 100,500,1000 \
    --alphas 0.8,1.0,1.2 \
    --seed 42 \
    --runs 3 \
    --output ./build/lfu_benchmark_results
```

Этот пример выполняет 27 отдельных запусков кеша. `--runs 3` использует seed
42, 43, 44. Для каждой пары alpha/seed генерируется один поток, общий для всех
ёмкостей. В каждой проверке кеш изначально пустой; прогрев входит в статистику.
Здесь измеряется качество кеширования (хиты), а не скорость работы.

Все параметры, кроме `--cache-bin`, необязательны. Значения по умолчанию такие
же, как в примере, кроме `--runs 1` и `--output lfu_benchmark_results`.
`--help` выводит справку. `--self-test` запускает только фиксированные случаи.

## Модель запросов

Ключи и значения — `int`. Для генерируемых потоков ключи лежат в `1..N`, где
`N = --keys`. Ключ одновременно является рангом популярности:

```text
P(key = k) = k^(-alpha) / sum(j^(-alpha), j = 1..N)
```

Ключ 1 самый популярный. При `alpha=1` его вероятность вдвое больше вероятности
ключа 2 и в десять раз больше вероятности ключа 10. Больший alpha усиливает
концентрацию запросов на первых ключах. Конечный набор позволяет использовать
любое конечное `alpha > 0`, в том числе значения меньше единицы.

Реализация использует веса `1 / pow(k, alpha)`, `std::discrete_distribution<int>`
и `std::mt19937_64`. Это независимые запросы со стационарной популярностью:
модель не добавляет пользовательские сессии, всплески и изменение популярности.
Она не воспроизводит все свойства настоящего трафика.

Формула: [NIST: Zipf probability mass function](https://www.itl.nist.gov/div898/software/dataplot/refman2/auxillar/zippdf.htm).
Применение такой модели к кешированию:
[Web Caching and Zipf-like Distributions](https://pages.cs.wisc.edu/~cao/papers/zipf-implications.html).

Одинаковые параметры и seed дают одинаковый поток при той же реализации
стандартной библиотеки. `std::discrete_distribution` не гарантирует одинаковую
последовательность между разными STL; для точного воспроизведения сохраняйте `.in`.

## Результаты и повторный запуск

Каждый запуск создаёт новый каталог `run-XXXXXX` внутри `--output` и печатает
его путь. Предыдущие результаты сохраняются. В каталоге находятся:

- `results.csv`: параметры каждого случая, `hits`, `misses`, `hit_rate`,
  `reference_hits`, `status`.
- `*.in`: входной поток для соответствующей ёмкости.
- `*.out`: фактический stdout `LFU-cache`.
- `*.err`: stderr `LFU-cache`.

`hit_rate` в CSV — доля от 0 до 1, в терминале — проценты. Для пустого потока
выводится 0. Имена `zipf_a0_run0_c0` используют индексы в переданных списках;
конкретные значения записаны в CSV.

Формат входа соответствует текущему `modules/source/LFU_cache.cpp`:

```text
число_запросов ёмкость_кеша
ключ_1
ключ_2
...
```

Повторить сохранённый случай можно так, заменив путь на напечатанный каталог:

```sh
./build/modules/LFU-cache < build/lfu_benchmark_results/run-XXXXXX/zipf_a0_run0_c0.in
```

Эталон хранит упорядоченные тройки `(частота, момент_последнего_доступа, ключ)`
в `std::set`. Он вытесняет элемент с минимальной частотой, а при равенстве —
с самым старым доступом. Частота нового или повторно загруженного ключа равна 1.
Это отдельная реализация без кода LFU и без его списков/итераторов,
со сложностью `O(число_запросов * log(ёмкость))`.

`PASS` означает совпадение числа хитов с эталоном. `FAIL` — несовпадение;
`ERROR` — ошибка запуска, аварийное завершение, таймаут или некорректный stdout.
Для каждого дочернего процесса установлен таймаут 30 секунд. Код возврата
бенчмарка — 0 только при успехе всех случаев, иначе 1.

Число запросов ограничено диапазоном неотрицательного `int`, поскольку текущая
программа LFU использует `int` для счётчика хитов и индекса запроса. Поток и
веса хранятся в памяти: `O(requests + keys)`. Вход сохраняется отдельно для
каждой ёмкости, поэтому большие серии требуют соответствующего места на диске.
